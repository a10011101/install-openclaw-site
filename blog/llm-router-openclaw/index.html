OpenClaw Fallback Model: Router, Failover, and the Next Answer

An OpenClaw fallback model is the next model in the chain. It answers this turn. It does not replace the primary.

An OpenClaw fallback model is the next model OpenClaw tries after the current one fails. It is not a second assistant, and it is not a new install. Memory, skills, and channels stay where they are. Only the model attempt changes.

OpenClaw is the assistant. The model is the engine for one attempt. If that engine is rate limited, overloaded, or silent, the fallback list is the ordered plan for the rest of this turn. The next turn starts on the primary again.

A router and a fallback list are easy to mix up. A model router chooses which upstream a request may reach. An OpenClaw fallback model is what runs after that request already failed. You can use both. They are not the same setting.

What an OpenClaw Fallback Model Does

The configured default lives at agents.defaults.model.primary. The ordered list lives at agents.defaults.model.fallbacks. OpenClaw walks that list only when the failure is worth failing over. A wrong key, a user cancel, and a hard timeout are not the same event.

Set the chain from the CLI, or write the same list in config:

openclaw models fallbacks list
openclaw models fallbacks add openai/gpt-5.4-mini
openclaw models fallbacks remove openai/gpt-5.4-mini
{
  "agents": {
    "defaults": {
      "model": {
        "primary": "anthropic/claude-sonnet-4-6",
        "fallbacks": ["openai/gpt-5.4-mini", "ollama/qwen3.5:27b"]
      }
    }
  }
}

Order is the policy. Put the model you want next in the first slot, not the cheapest model you happen to have a key for. A fallback that cannot call tools will finish the turn with a weaker answer, and you will blame the primary. Compare candidates in choosing an OpenClaw LLM before you add a third name.

The winning fallback answers this turn only. OpenClaw does not save it as the session model. Status can show that a fallback answered. The next message still starts on the selected primary, unless you pinned a different model yourself.

OpenClaw Model Router vs the Fallback List

An OpenClaw model router is a provider that fronts many upstream models with one credential and one catalog. ClawRouter is the bundled router. You point OpenClaw at it, and the key's policy decides which models appear.

The fallback list does not care how you reached the primary. Your primary can be a ClawRouter ref, and the next OpenClaw fallback model can be a direct provider or a local model. The router controls access and budget. The fallback list controls recovery.

Do not list the same model twice under two names. If both refs hit the same key, the second attempt fails for the same reason. A real second hop uses a different provider, or a self-hosted LLM that does not share that key.

LLM Router OpenClaw: ClawRouter

ClawRouter ships with OpenClaw. The provider id is clawrouter. The default origin is https://clawrouter.openclaw.ai. Auth is the CLAWROUTER_API_KEY environment variable. Do not paste that key into a chat or a commit.

openclaw onboard --auth-choice clawrouter-api-key
openclaw models list --all --provider clawrouter
openclaw models set clawrouter/openai/gpt-5.5

Use the refs the catalog returns, such as clawrouter/openai/gpt-5.5. If plugins.allow is set, add clawrouter. For a private deployment, set models.providers.clawrouter.baseUrl and store the key as an env reference on apiKey.

An empty catalog is usually the key's policy, not a broken install. ClawRouter checks grants and budget when the request is sent. The router does not replace agents.defaults.model.fallbacks. If the routed model times out, OpenClaw still walks your fallback list. A router outage with an empty list is a single point of failure.

OpenClaw Model Failover, in Order

OpenClaw model failover has two stages before it gives up.

First it stays on the same model. Temporary rate limits get a bounded retry on the current transcript. Auth profiles for that provider rotate when the failure calls for a different credential. Overloaded and rate-limit errors allow one same-provider profile rotation by default, then the chain moves on.

Second, if that provider is exhausted, OpenClaw moves to the next OpenClaw fallback model. Each candidate gets its own attempt budget. agents.defaults.timeoutSeconds applies per attempt, so a long chain can outlast one timeout setting. A user cancel stops the whole chain. A final run timeout, or the idle-timeout cost breaker, also stops it. Those stops are terminal. They are not a request to try the next model.

These sources are allowed to use the configured fallbacks:

  • The configured default primary.
  • A cron job model, unless that job sets payload.fallbacks. An empty list makes the job strict. See OpenClaw cron jobs for the schedule.
  • An agent model object that includes its own fallbacks.

These sources are strict:

  • A model you picked with /model, the model picker, or sessions.patch. If it fails before a reply, OpenClaw reports the error. It does not quietly answer from another model.
  • An agent primary with no fallbacks of its own. Set fallbacks to an empty list when you want that strict behavior written down.

A transcript write conflict does not change models. If the run looks like a hang, start with the OpenClaw timeout guide. A model that never sends a token needs a longer provider clock or a faster model. Adding fallbacks does not fix a primary that is still loading weights.

OpenClaw LLM Proxy

An OpenClaw LLM proxy is a gateway in front of provider APIs. LiteLLM is the usual self-hosted one. Cloudflare AI Gateway is another. You onboard the proxy as a provider, and OpenClaw sends model calls to that base URL.

openclaw onboard --auth-choice litellm-api-key

The proxy can do its own backend routing, spend limits, and logs. That routing is not OpenClaw's fallback list. If LiteLLM fails over inside one request, OpenClaw still sees one provider. If the proxy host is down, only the next OpenClaw fallback model on a different provider will answer.

Use a proxy for one bill and one key policy. Use the fallback list for a second provider that does not share that outage. Keep the proxy key in the auth store or an env reference, and put a custom origin on the provider baseUrl.

OpenClaw Multi Model Routing That Stays Boring

OpenClaw multi model routing is three decisions, not a mesh of agents.

  1. Primary: the model that should answer a normal chat turn.
  2. Fallbacks: one or two models that can finish a failed turn, on a different provider if you can.
  3. Optional utility model: a cheaper model for short internal work such as titles. That is not the chat fallback. imageModel is also separate. It runs when the primary cannot accept images.

Skip a long chain. Two fallbacks are enough for a personal gateway. A five-model list hides a bad primary and spends the attempt budget on models you would not trust. The multi-model setup is about roles, not logos.

Run openclaw models fallbacks list, then send one prompt that must use a tool while the primary is stopped. A greeting does not prove failover. If you pinned the fallback with /model during the test, run /model default so the next turn returns to the configured primary.

Pair a strong primary with a cheaper fallback only for outages, not for every cron run. The cheapest LLM for OpenClaw is a cost choice. An OpenClaw fallback model is an availability choice. They can be the same model. They usually should not be.
