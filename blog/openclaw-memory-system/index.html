How OpenClaw's Memory System Works

// architecture April 17, 2026 11 min read

One of the most common questions people ask after installing OpenClaw is: "How does it actually remember things?" The answer is more interesting — and more practical — than most people expect. Unlike cloud AI assistants that store a hidden conversation history somewhere on vendor servers, OpenClaw's memory is entirely file-based, transparent, and under your control.

This post is a thorough walkthrough of how the memory system works: the two-tier memory architecture (MEMORY.md vs daily files), how heartbeats keep your assistant aware between conversations, how cron jobs extend that awareness into scheduled action, and how everything survives server restarts. By the end you'll understand not just what the system does, but why it's designed this way — and how to get the most out of it.

TL;DR: OpenClaw memory lives in plain Markdown files on your server. MEMORY.md is curated long-term memory. Daily files (memory/YYYY-MM-DD.md) are raw session logs. Heartbeats keep the assistant proactive between chats. Cron jobs handle scheduled tasks. All of it persists across restarts because it's just files — no database, no vendor dependency.

The Problem: AI Assistants Are Amnesiac by Default

Every standard AI assistant — ChatGPT, Claude, Gemini — suffers from the same architectural limitation: they're stateless. Each new session starts from zero. The model has no idea who you are, what you were working on yesterday, what decisions you made last week, or what your preferences are. You have to re-explain your context every single time.

This isn't an accident. It's a consequence of how these systems are designed — short-term context windows, no persistent storage, no connection between conversations. The result is that even if you use an AI assistant every day for months, it never knows you. It's perpetually meeting you for the first time.

OpenClaw solves this with a simple but powerful design principle: memory is just files. Files that persist. Files that the assistant reads at the start of every session. Files that it writes to as things happen. Files that you can inspect, edit, and understand. No black boxes.

The Two-Tier Memory Architecture

OpenClaw uses two distinct layers of memory, each serving a different purpose. Understanding the difference is the key to understanding the whole system.

Tier 1: MEMORY.md — Long-Term, Curated Memory

MEMORY.md is the equivalent of your AI assistant's long-term memory — the kind of things a human would remember about a colleague they've worked with for a year. It's not a transcript of conversations. It's curated, distilled knowledge about you, your preferences, your projects, and your context.

What goes in MEMORY.md?

  • Your name, how you like to be addressed, your timezone
  • Ongoing projects and their current status
  • Decisions you've made and why
  • Things you explicitly asked the assistant to remember
  • Lessons learned from past interactions
  • Your communication style preferences
  • Important recurring context (your team, your tools, your workflow)

MEMORY.md is loaded at the start of every main session — the direct conversation between you and your assistant. It's intentionally not loaded in shared contexts like group chats or Discord servers, for the obvious reason that it contains personal information that shouldn't be visible to strangers.

Important design choice: MEMORY.md is only for the main session. This is a deliberate privacy boundary. When your assistant participates in a group chat, it doesn't have access to your personal long-term memory — only to the current conversation context.

The assistant can read, edit, and update MEMORY.md freely. If you say "remember that I prefer short responses", it writes that to MEMORY.md. If a project changes status, it updates the entry. The file is yours to read and edit too — there's nothing opaque about it.

Tier 2: Daily Memory Files — Raw Session Logs

The second tier is the memory/ directory, which holds date-stamped files in the format memory/YYYY-MM-DD.md. These are raw logs of what happened each day — the equivalent of a notebook you scribble in during a meeting, versus the refined notes you'd write up afterwards.

At the start of each session, the assistant reads today's file and yesterday's file. This gives it a working memory of recent events without having to load everything that's ever happened. The pattern is:

# memory/2026-04-17.md

## 09:14 — Main session
User asked me to draft the Q2 report outline.
Drafted outline with 6 sections, sent via Telegram.
Reminded to follow up with the finance team by Thursday.

## 14:30 — Heartbeat check
Email inbox: 3 new messages, none urgent.
Calendar: board call tomorrow at 10am. Flagged to user.

## 16:45 — Main session
User approved the outline. Began drafting section 1.
Decision: use the 2025 data for baseline comparisons.

Daily files serve several purposes: they give the assistant recent context when a session starts, they form a searchable audit trail of what happened and when, and they're the raw material from which MEMORY.md gets updated.

The Memory Maintenance Loop

Over time, daily files accumulate. Left alone, they'd eventually contain months of raw logs that would be expensive to load in full. OpenClaw handles this with a maintenance loop: periodically (usually during a heartbeat), the assistant reviews recent daily files, extracts insights worth keeping long-term, and distills them into MEMORY.md. Stale or redundant information in MEMORY.md gets pruned.

Think of it like a person reviewing their notebook and updating their mental model. The daily file is the notebook. MEMORY.md is the mental model — smaller, more organized, and far more useful for ongoing context.

How Sessions Work: Starting Fresh, But Not Empty

Each OpenClaw session starts fresh — a new conversation, a clean context window. But "fresh" doesn't mean "empty". At session start, the assistant loads:

  1. SOUL.md — the persona and behavioral guidelines (who the assistant is)
  2. USER.md — basic information about you (name, timezone, preferences)
  3. MEMORY.md — long-term curated memory (main session only)
  4. Today's and yesterday's daily files — recent context
  5. Any injected workspace files — project-specific context

The result: by the time you send your first message, your assistant already knows who you are, what you were working on yesterday, what decisions are pending, and what your current context looks like. You don't have to re-introduce yourself or re-explain your projects. The session picks up where the last one left off.

Real example: You close a Telegram conversation at 11pm on Tuesday after discussing a client proposal. On Wednesday morning you say "anything new?". Your assistant has already read Tuesday's daily file, knows about the proposal, and can immediately respond with relevant context — what was decided, what's still open, and what it noticed during overnight heartbeats.

Heartbeats: Keeping Your Assistant Aware Between Sessions

Memory files solve the problem of persistence across sessions. But they don't solve a different problem: what happens between sessions? If your assistant only ever acts when you message it, you lose a huge chunk of its potential value — the proactive, initiative-taking behavior that makes it genuinely useful rather than just reactive.

That's what heartbeats are for.

A heartbeat is a scheduled poll — a message sent to the assistant on a regular interval (every 15–60 minutes is typical) that wakes it up and asks: is there anything worth doing or flagging right now?

The assistant responds to a heartbeat by running through its configured checklist. Typical heartbeat tasks:

// inbox

Email Check

Scan unread messages. Flag anything urgent, time-sensitive, or requiring a decision. Ignore noise. Batch low-priority items for a morning summary.

// calendar

Calendar Watch

Look for events in the next 24–48 hours. Notify proactively when something is approaching — especially if prep work is needed.

// weather

Weather & Context

Surface relevant environmental context. Is it going to rain during your planned outdoor meeting? Worth a heads-up.

// projects

Project Status

Check git status, pending PRs, open tasks, or stale issues. Flag anything that's been quiet too long or needs attention.

The key design principle of heartbeats is quality over quantity. If there's nothing worth flagging, the assistant responds with a quiet OK and logs the check. It does not send you a notification just to prove it ran. You don't want to be spammed; you want to be informed when it matters.

Heartbeat state is tracked in a JSON file (typically memory/heartbeat-state.json), which records the timestamp of each check type. This prevents redundant checks — if the assistant checked email 10 minutes ago, it won't check it again on the next heartbeat.

{
  "lastChecks": {
    "email": 1745004800,
    "calendar": 1745001200,
    "weather": null
  }
}

Heartbeats also handle proactive background work: updating documentation, committing and pushing workspace files, reviewing memory files, and performing maintenance tasks that don't need your involvement. Your assistant can do productive work while you sleep.

Cron Jobs: Scheduled, Isolated Tasks

Heartbeats are great for periodic checks that benefit from conversational context. But some tasks need exact timing, need to run independently of the main session, or need a different model or isolation level. That's where cron jobs come in.

OpenClaw supports a cron-style scheduling system for tasks like:

  • Daily digest emails — summarize the day's activity and send it to you at 8am sharp
  • Weekly reports — compile a project status report every Monday morning
  • One-shot reminders — "remind me about this in exactly 2 hours"
  • Monitoring jobs — check an external service every 5 minutes and alert on failure
  • Cleanup tasks — archive old files, prune logs, tidy the workspace at midnight

The practical difference between heartbeats and cron is timing precision and context. Heartbeats can drift — "roughly every 30 minutes" is fine. Cron jobs fire at exact times. Heartbeats share the main session context. Cron jobs run in isolation, which means they don't pollute your conversation history with background noise.

Feature Heartbeat Cron Job
Timing precision Approximate (can drift) Exact schedule
Shares session context Yes — conversational memory Isolated — clean slate
Best for Batched checks, background work Timed tasks, standalone jobs
Output delivery May surface to main session Direct to channel
API cost efficiency Batches multiple checks One task per invocation

A practical rule: if you're thinking "check every ~30 min whether anything needs attention", use a heartbeat. If you're thinking "send me a report at 9am every Monday", use cron.

Surviving Restarts: Why File-Based Memory Is the Right Choice

Here's where the design really shines. Because all memory is stored in plain files on your server's filesystem, it survives everything:

  • Process crashes — the files are on disk, not in RAM
  • Server reboots — systemd starts OpenClaw back up, it reads the files, picks up where it left off
  • Model upgrades — switch from Claude to GPT-4 to Gemini; the memory files are model-agnostic
  • OpenClaw updates — update the runtime, the memory remains intact
  • Migration to a new server — rsync the workspace directory, everything moves with it

There's no database to back up, no vendor API to stay synced with, no hidden state to worry about. Your assistant's memory is as durable as your filesystem. If you run backups (and you should), your assistant's entire context is included automatically.

This is a deliberate departure from how most AI products work. Most cloud AI products store your conversation history on their servers, in formats you can't inspect or control. If they go down, change their API, or discontinue the product, your history is gone or inaccessible. With OpenClaw, you own the files. They're yours, in plain text, forever.

Practical Usage: Getting the Most from the Memory System

Explicit Memory Commands

You can always tell your assistant to remember something explicitly:

  • "Remember that I prefer bullet points over paragraphs for summaries"
  • "Note that the client project has moved to phase 2 as of today"
  • "Update my profile: I've switched to using VS Code instead of Vim"

The assistant will write these to MEMORY.md immediately. On next session load, the updated context will be there.

Querying Memory Directly

Because memory is in files, you can ask the assistant to look things up:

  • "What did we decide about the API architecture last week?"
  • "What was the client's feedback on the last proposal?"
  • "When did I last update the project documentation?"

The assistant can search its daily files and MEMORY.md to surface answers. It's not perfect recall — it depends on what was written down — but if you've been using OpenClaw consistently, the paper trail is usually there.

Cross-Context Memory Safety

OpenClaw's memory system has a built-in privacy model. MEMORY.md (which contains personal context) is only loaded in the main session. In group chats, the assistant operates on the current conversation alone. You never have to worry about your assistant accidentally leaking personal information into a group context because it simply doesn't have that information loaded.

Skills can also store their own state — in JSON files, in the workspace, in skill-specific directories. The Shopify skill might track last sync times; the GitHub skill might cache PR status. These are separate from your personal memory and managed by each skill independently.

Memory Hygiene

Over months of use, MEMORY.md can grow stale — outdated project entries, obsolete preferences, context that no longer applies. The assistant periodically prunes this during heartbeats, but you can also prompt it manually:

  • "Do a memory review — clean up anything outdated"
  • "Archive the project X entries from MEMORY.md"
  • "Read through last month's daily files and update MEMORY.md with anything important"

The goal is a MEMORY.md that stays tight and relevant — the distilled essence of what matters — not a sprawling dump of everything that's ever happened.

How This Compares to Cloud AI Memory Features

Major AI providers have started adding "memory" features to their products. OpenAI added memory to ChatGPT; Google has history in Gemini. These are better than nothing, but they're fundamentally different from OpenClaw's approach:

  • Opacity: You can't easily read or edit what they've stored about you. OpenClaw's memory is a text file you can open in any editor.
  • Ownership: Vendor-side memory belongs to the vendor. Your OpenClaw memory files belong to you.
  • Portability: If you switch AI providers, your OpenClaw memory goes with you. Cloud memory is tied to the platform.
  • Scope: Vendor memory captures conversation snippets. OpenClaw memory is actively maintained, curated, and can include anything you want — including context from outside the AI conversation itself.
  • Privacy: Cloud memory trains on or informs future model behavior. OpenClaw memory stays on your server.

The Bigger Picture: Memory as Identity

There's something worth reflecting on here. For an AI assistant, memory is identity. Without memory, every conversation is with a stranger. With memory, you're talking to someone who knows you — your history, your preferences, your context, your ongoing work.

OpenClaw's file-based memory system makes that possible not through some proprietary magic, but through the most durable and transparent mechanism available: text files on disk. MEMORY.md is your assistant's accumulated self. Daily files are its journal. Heartbeats are its awareness between conversations.

Together, these form a system that gives you an AI assistant that genuinely persists — that you can build a real working relationship with over months and years, rather than starting over every morning.

That's the design. And it works remarkably well.
